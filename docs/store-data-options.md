# 우리 가게 데이터 연결 방식 선택지

이 문서는 앞으로 무엇을 만들지 고르기 위한 비교입니다. **아래 방식은 아직 실제 가게 데이터에 사용할 수 있도록 완성되지 않았습니다.** 현재 합성 화면의 로그인과 저장은 실제 개인정보 보호나 업무 기록 보관을 제공하지 않습니다. 최종 방식은 basoon(바순)이 결정합니다.

비교 기준은 앱 하나, 개발자 한 명, 기존 데이터를 조금 가져와 한 가게에서 시험하는 경우입니다. 기간은 구현과 기본 검증을 포함한 거친 예상으로, 데이터 형식·권한 요구·외부 서비스 계약·디자인 결정에 따라 달라집니다. 법률 검토, 여러 앱의 전체 연결과 운영 대행은 포함하지 않습니다.

| 방식 | 어떤 가게에 맞나 | 난이도와 예상 작업량 | 개인정보·백업·권한에서 챙길 점 |
| --- | --- | --- | --- |
| **1. 로컬 파일 가져오기** | 한 사람이 자기 컴퓨터에서 기존 CSV 같은 파일을 골라 내용을 확인할 때 | 낮음~중간. 한 앱의 읽기 전용 가져오기와 오류 확인에 대략 **3~7일** | 원본 파일·내보낸 파일·임시 파일에도 개인정보가 남을 수 있습니다. 열 이름·형식·중복을 확인하고, 가져오기 전 원본을 따로 보관해야 합니다. 컴퓨터 계정과 파일 접근 권한을 나누지 않으면 다른 사람이 볼 수 있습니다. 여러 직원이 동시에 수정하는 저장소로 쓰기에는 부적합합니다. |
| **2. 한 컴퓨터의 로컬 DB** | 한 가게가 한 컴퓨터에서 데이터를 지속적으로 조회·수정할 때 | 중간. 예를 들어 SQLite를 사용해 한 앱의 저장·검증·백업·복구를 만드는 데 대략 **2~4주** | 컴퓨터 분실·고장과 DB 손상에 대비해 암호화, 별도 장소 백업과 복구 시험이 필요합니다. 파일을 공유 폴더에 두고 여러 컴퓨터에서 동시에 여는 방식은 잠금 문제가 생길 수 있습니다. 로그인·직원별 권한은 DB를 쓴다고 자동으로 생기지 않습니다. |
| **3. 가게가 관리하는 서버 연결** | 여러 직원이나 여러 기기가 같은 자료를 함께 써야 할 때 | 높음. 한 앱의 서버·DB·계정·권한·백업과 운영 점검에 대략 **4~8주 이상** | 인터넷에 연결되는 만큼 로그인과 서버 측 권한 검사, 통신 보호, 기록·복구·보안 업데이트와 운영 책임자를 마련해야 합니다. 서버와 저장소 비용이 들 수 있고 장애 대응도 필요합니다. |

## 처음 시작할 때의 권장 순서

1. **합성 자료로 업무 흐름부터 확인합니다.** 실제 고객·직원 정보는 넣지 않습니다.
2. 한 컴퓨터에서 조회만 필요하다면 **파일 가져오기**를 먼저 시험합니다. 항목 대응, 중복과 오류를 확인하고 원본을 별도 보관합니다. 파일을 읽는 것과 안전하게 업무 데이터를 저장하는 것은 별개입니다.
3. 기록을 고치고 계속 보관해야 한다면 **로컬 DB**를 검토합니다. 저장 위치, 컴퓨터 접근, 별도 백업과 복구를 먼저 정하고 시험합니다.
4. 직원들이 동시에 쓰거나 외부에서 접근해야 한다면 **가게가 관리하는 서버**를 검토합니다. 누가 무엇을 볼 수 있는지와 퇴사자 접근 해제, 백업·복구, 비용과 운영 담당을 결정한 뒤 연결합니다. 여러 기기가 필요하면 로컬 단계를 억지로 거칠 필요는 없습니다.

파일이나 DB를 다른 앱에 연결하기 전에 어떤 항목을 누가 어떤 목적으로 사용할지 확인하고, 개인정보처리방침과 이용약관이 필요한 경우 각 가게가 자기 운영에 맞게 직접 준비해야 합니다. 이 저장소는 가게별 법률 문서를 대신 제공하지 않습니다.

## 구현을 고르기 전에 확인할 것

- 첫 대상 앱과 필요한 항목, 읽기만 할지 수정할지, 한 번에 사용할 사람 수
- 기존 파일 형식과 잘못된 행·중복 자료를 처리하는 방법
- 저장 위치, 열람·수정 권한, 비밀번호와 접속 열쇠 관리
- 자동 또는 수동 백업 주기, 별도 보관 위치, 실제 복구 시험 담당자
- 여러 기기 사용과 인터넷 접근 필요 여부, 서버 비용과 고장 대응 담당자
